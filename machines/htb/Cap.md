# HackTheBox — Cap

**Platform:** HackTheBox | **OS:** Linux | **Difficulty:** Easy | **Status:** Retired  
**Release Date:** 05 Jun 2021  
**CVEs Covered:** None — logic flaw (IDOR) + Linux capability misconfiguration  
**Tools Used:** Nmap, Wireshark / tshark, FTP, SSH, getcap, Python

---

## Summary

Cap is an Easy-rated Linux machine that demonstrates how two ordinary misconfigurations — one in an application, one in the OS — chain into a full root compromise without a single CVE. The foothold exploits an **Insecure Direct Object Reference (IDOR)** in a Flask "Security Dashboard" web app: the packet-capture feature stores each capture at a sequential, predictable URL (`/data/<id>`), and changing the ID to `0` returns a capture that doesn't belong to the current session. That capture contains a plaintext FTP login, because FTP transmits credentials unencrypted. The recovered password (`nathan:Buck3tH4TF0RM3!`) is reused for SSH, yielding the user flag. Privilege escalation abuses a **Linux capability misconfiguration**: `/usr/bin/python3.8` carries `cap_setuid+ep`, allowing any user to set their UID to 0 and spawn a root shell. The box is a clean lesson in why predictable object references and over-privileged binaries are both critical findings.

---

## Attack Chain Overview

```
Nmap → 21/FTP, 22/SSH, 80/HTTP (gunicorn "Security Dashboard")
→ /capture creates a pcap at /data/<id> (IDOR)
→ Change id to /data/0 → download earlier capture
→ Analyze pcap → plaintext FTP creds (nathan:Buck3tH4TF0RM3!)
→ Reuse over SSH → user.txt
→ getcap -r / → /usr/bin/python3.8 = cap_setuid+ep
→ python3.8 os.setuid(0) → root shell → root.txt
```

## 2. Web Enumeration

### The Security Dashboard

Browsing to `10.129.6.116` serves a "Security Dashboard" presenting fake security metrics for the host. Three sidebar features stand out:

- **Security Snapshot (PCAP + Analysis)** — captures live network traffic on the server and presents an analysis.
- **IP Config** — output of `ifconfig` on the server.
- **Network Status** — output of `netstat`.

### The Snapshot Feature

Clicking **Security Snapshot** triggers a server-side packet capture and redirects the browser to a results page at a numbered path:

```text
http://10.129.6.116/data/1
```

The page summarizes the capture (packets sent/received, etc.) and offers a **Download** link for the raw `.pcap`. The number in the URL is a **sequential capture ID** tied to the request — and nothing prevents requesting an ID that isn't ours.

## 3. Exploitation — Insecure Direct Object Reference (IDOR)

### Vulnerability Explanation

The dashboard stores every snapshot at a predictable, sequential URL — `/data/0`, `/data/1`, `/data/2` … — and performs **no authorization check** binding a capture to the session that created it. Any visitor can enumerate IDs and download captures belonging to other sessions. This is a textbook **IDOR**: the object reference (the capture ID) is exposed directly and the server trusts the client to only request its own.

The most valuable target is `/data/0` — typically the earliest capture, often generated during setup or testing when an administrator's own traffic was on the wire.

### Exploiting It

Walk the ID backwards to `0`:

```text
http://10.129.6.116/data/0
```

The summary for capture `0` shows a higher packet count than the empty captures generated by our own clicks — a strong signal it contains real traffic. Download the raw capture:

```bash
wget http://10.129.6.116/data/0/download -O 0.pcap
```

## 4. Credential Recovery

### Analyzing the Capture

Open the capture in Wireshark, or carve the FTP control channel from the command line with `tshark`:

```bash
tshark -r 0.pcap -Y 'ftp' -T fields -e ftp.request.command -e ftp.request.arg
```

```text
USER    nathan
PASS    Buck3tH4TF0RM3!
```

Because FTP authentication is unencrypted, the `USER` and `PASS` commands sit in cleartext inside the capture. In Wireshark, the same result comes from **Follow → TCP Stream** on the FTP conversation, or filtering on `ftp`.

Recovered credentials:

```text
nathan : Buck3tH4TF0RM3!
```

### Validating Credential Reuse

The credentials authenticate against FTP, but FTP only exposes Nathan's home directory. The real prize is checking whether the password is **reused on SSH** — and it is.

```bash
ftp 10.129.6.116      # nathan / Buck3tH4TF0RM3!  → works, but limited
```

uid=1001(nathan) gid=1001(nathan) groups=1001(nathan)

Nathan is an unprivileged user with no `sudo` rights:

```bash
sudo -l
# (prompts for password / no sudo entry)
```

### Hunting for Linux Capabilities

Standard SUID hunting is unremarkable, so pivot to **file capabilities** — a frequently overlooked privilege-escalation surface on modern Linux:

```bash
getcap -r / 2>/dev/null
```

```text
/usr/bin/python3.8 = cap_setuid,cap_net_bind_service+ep
```

**`/usr/bin/python3.8` carries `cap_setuid+ep`.** This is the entire privilege-escalation path: a full Python interpreter that is permitted to change its own UID to anything — including `0` (root).

## 7. Privilege Escalation — Python `cap_setuid` Capability Abuse

### Vulnerability Explanation

Linux **capabilities** split root's powers into discrete units that can be granted to individual binaries without making them full SUID-root. `cap_setuid` grants one specific power: the ability to call `setuid()` and arbitrarily change the process's user ID. Granting it to a general-purpose interpreter like Python is catastrophic — the interpreter will run *any* code the user supplies, so the user can simply instruct it to become root.

The `+ep` flags mean the capability is **Effective** (active immediately) and **Permitted** (allowed for the binary). No race, no exploit binary, no password required — just one line of Python.

### Getting Root

```bash
/usr/bin/python3.8 -c 'import os; os.setuid(0); os.system("/bin/bash")'
```

`os.setuid(0)` drops the process to UID 0 using the granted capability, then spawns a Bash shell that inherits root:

```bash
whoami
# root
id
# uid=0(root) gid=1001(nathan) groups=1001(nathan)
```

```bash
cat /root/root.txt
```

## Lessons Learned

**Predictable object references are an authorization failure, not a UI quirk.** The snapshot feature worked perfectly — it just trusted the client to only ask for its own captures. IDOR is one of the most common real-world web vulnerabilities precisely because sequential IDs feel harmless during development. Any endpoint that maps a guessable identifier to per-user data must enforce an ownership check on every request.

**Plaintext protocols turn one capture into a credential dump.** FTP sends `USER` and `PASS` in cleartext. The IDOR alone was only a data-exposure bug — it became a foothold because the exposed data was a packet capture of an unencrypted login. Layered weaknesses compound: a low-severity disclosure plus a plaintext protocol equals account takeover.

**Credential reuse bridges services.** The FTP password was identical to the SSH password. Always test recovered credentials against every authentication surface on the host, not just the service they came from.

**Linux capabilities are SUID's quieter cousin — always enumerate them.** `getcap -r /` is a one-line check that `find / -perm -4000` will never reveal. `cap_setuid` on an interpreter is functionally equivalent to a SUID-root shell. When hardening, capabilities should be scoped to purpose-built binaries, never to general interpreters like Python, Perl, or Ruby.
